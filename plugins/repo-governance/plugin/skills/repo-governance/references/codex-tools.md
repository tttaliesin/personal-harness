# Codex Desktop 연결

Node.js 22.18 이상, npm, Git, Task 3과 Codex Desktop이 필요하다.
터미널에서 `codex --version`으로 Codex CLI 실행을 확인한다.

## 설치

1. 설치 폴더에서 `task setup:codex`를 실행한다.
2. Desktop에서 [실행 전 검사 훅 신뢰](#실행-전-검사-훅-신뢰)의 상태를 확인한다.

명령은 배포본을 검증하고 해당 배포본을 Codex CLI로 설치한다.
출력의 `scope: verified-installed-files`는 설치된 파일이 지정한 배포본과 일치한다는 뜻이다.

## 저장소 도입

설치 폴더에서 대상 Git 저장소를 한 번 지정한다.

```sh
task adopt TARGET="제품폴더"
```

같은 복제본의 연결된 worktree는 도입 기록을 공유한다.
작업할 폴더를 앱에서 프로젝트로 연다.
제품별 출력 경계와 외부 계약이 필요하면 [제품 설정](repository-policy.md)을 사용한다.

## 실행 전 검사 훅 신뢰

**설정 → Hook → Repo Governance**에서 실제 명령과 범위를 확인한다.
앱이 검토를 요청한 경우 해당 훅을 신뢰하고 활성 상태를 확인한다.
훅이 **변경됨** 상태면 Codex는 해당 훅을 건너뛴다.
배포본을 갱신한 뒤에는 새 작업 대화를 열기 전에 신뢰 상태를 확인한다. [Codex 훅 신뢰 안내](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks)
범위가 **모든 프로젝트**이면 이 훅은 모든 프로젝트의 도구 호출에서 실행될 수 있다.
훅은 대상 저장소의 도입 여부를 확인한다.
미도입 저장소는 일반 작업을 계속한다.

## 새 대화에서 스킬 사용

에이전트에 평소 작업을 요청한다.
필요할 때 `$repo-governance`로 명시한다.
예를 들어 새 팀원이 첫 실행 경로를 찾을 수 있도록 README를 정리해 달라고 요청한다.
스킬은 실제 명령과 예시를 찾아 문안을 제안한다.
훅은 실제 커밋에 들어갈 README, 파일과 메시지를 확인한다.

## 설치 갱신과 문제 해결

새 설치 폴더에서 `task update:codex`를 실행한다.
다른 폴더를 지정하려면 `task update:codex SOURCE="새설치폴더"`를 실행한다.
명령이 끝나면 Desktop의 [훅 신뢰와 활성 상태](#실행-전-검사-훅-신뢰)를 확인한다.
호환되는 설정과 저장소 도입은 기존 기록을 사용한다.

| 현상 | 확인할 곳 |
| --- | --- |
| 설치 파일 누락 | 설치 폴더에서 `task verify:bundle`로 실제 파일과 manifest를 대조한다. |
| 자동 검사 미적용 | **설정 → Hook → Repo Governance**에서 신뢰·활성 상태를 확인한다. 시험할 저장소의 도입 기록을 확인한다. |
| 구형 설정 누락 또는 손상 | [제품 설정](repository-policy.md#로컬-native-연결)에서 원본과 유효한 설정을 확인한다. |
| 이전 설치본으로 복구 | `task update:codex SOURCE="이전설치폴더"`를 실행한다. 이전 버전이 파일 해시 pin을 요구하면 보관한 해당 입력을 사용한다. |

## PR 생성과 제목·본문 수정

생성은 저장소·head·base·제목·본문을 모두 명시한 같은 GitHub.com 저장소의 후보를 지원한다.
구조화된 `create_pull_request`와 리터럴 `gh pr create`·공식 별칭 `gh pr new`는 같은 검사를 사용한다.
CLI는 `--repo`·`--head`·`--base`·`--title`과 `--body` 또는 `--body-file`을 명시한다.
`-b`는 본문, `-B`는 기준 브랜치이며 `--draft`의 생성 단계도 기록한다.
대상 브랜치를 추정하거나 원래 CLI의 자동 push에 맡기지 않는다.
native 연결은 head와 base의 원격 ref를 읽기 전용 GET으로 동시에 조회한다.
저장소 URL·정확한 ref·commit 유형·전체 OID가 일치하면 번호 없는 `pr-create` 후보로 K6를 검사한다.
기계 위반은 생성 전에 거절하며, 조회 실패·시간 초과·대상 불일치는 보류한다.
이슈 전환·fork·추가 권한 변경·생성 도구의 동적·복합·자동 작성 옵션은 지원하지 않는다.
조회는 각 4초로 제한하며 인증 정보와 원시 오류는 보고하지 않는다.

저장소와 PR 번호를 명시한 `gh pr edit`의 제목·본문·대상 브랜치 변경을 지원한다.
제목·본문은 `--title`·`--body`·`--body-file`로 지정한다.
본문 파일은 BOM 없는 UTF-8 일반 파일을 사용한다.
대상 브랜치는 `--base <branch>` 또는 `-B <branch>`로 지정한다.
구조화된 `update_pull_request`도 같은 검사를 사용한다.
구조화된 요청에는 `base_branch` 또는 `base` 중 한 필드로 대상을 지정한다.
연결부는 기존 gh 인증으로 GitHub.com의 해당 PR을 읽기 전용 조회한다.
`GH_HOST`가 다른 호스트를 지정하면 조회 전에 보류한다.
조회한 번호·저장소 URL·전체 head/base OID·제목·본문을 확인한 뒤 실제 수정 후보를 공통 `pull-request` 검사에 전달한다.
생략한 제목이나 본문은 조회한 값을 사용한다.
대상을 바꿀 때는 같은 저장소의 열린 PR인지 확인한다.
새 대상 브랜치가 현재 head 브랜치와 같으면 보류한다.
새 대상의 전체 ref를 읽기 전용 GET으로 조회하고 저장소·ref·commit 유형·전체 OID를 확인한다.
이 경우 K6에는 현재 head와 새 대상의 OID를 전달한다.
조회 실패·인증 부족·잘못된 응답·시간 초과는 수정을 보류한다.
준비 표시, PR 상태, 유지관리 권한을 바꾸는 요청은 보류한다.
조회와 실제 생성·수정 사이의 원격 변경이나 본문 파일 변경을 원자적으로 막는 기능은 제공하지 않는다.
작업 에이전트는 실제 PR의 저장소·head·base·제목·본문·draft 상태를 요청한 후보와 대조한다.

## 명시적인 squash 머지

기존 `gh pr merge`와 구조화된 `merge_pull_request`의 명시적인 squash 후보를 검사한다.
저장소·PR 번호·예상 head 전체 OID·최종 commit 제목과 본문을 모두 제공한다.
CLI는 `--squash`, `--match-head-commit`, `--subject`, `--body` 또는 `--body-file`을 사용한다.
연결은 실제 PR의 열린 상태·draft·충돌·검사·리뷰 상태와 예상 head를 읽기 전용으로 확인한다.
로컬 저장소의 원격 대상과 head/base 객체를 확인하고 base가 head의 조상인 경우 K6 PR 내용·K4 최종 메시지·K7 편입 파일을 같은 공통 검사기로 검사한다.
확인할 수 없는 조건과 미지원 머지 방식·관리자 우회·자동 머지·브랜치 삭제 요청은 보류한다.
서버의 실제 머지는 기존 도구가 수행하며 저장소의 유효한 조건을 그대로 적용한다.
예상 head 조건은 head 변경을 거절하는 데 사용하며 base와 최종 tree의 원자적 고정을 보장하지 않는다.
작업 에이전트는 현재 요청의 머지 허용과 실제 변경·검증의 의미를 확인하고 수행 뒤 결과를 대조한다.

## 실제 Desktop 검증

Desktop에서 시험 배포본의 설치와 훅 확인을 완료한다.
도입된 시험용 Git 저장소의 첫 대화를 연다.
정상 README 편집을 한 뒤 실제 커밋이 통과하는지 확인한다.
깨진 상대 링크가 있는 README 초안도 저장하고 stage한다.
그 상태로 커밋을 요청하면 훅이 `K3/link-missing`을 반환하며 HEAD가 유지돼야 한다.
작업 트리와 인덱스가 다를 때는 인덱스 내용으로 판정하는지 비교한다.
호환 설치본으로 갱신한 뒤에는 같은 저장소에서 정상 커밋을 다시 확인한다.

확인 방법과 증거는 [실제 연결 수용 절차](native-verification.md)를 참고한다.
실제 지원 상태는 [플러그인 안내](../../../README.md#검증과-지원-상태)에 기록한다.
