# K1 저장소 이름

저장소 목록에서 관리 책임을 좁혀 찾을 수 있게 `분류-대상[-관리범위]`를 권한다.
같은 제품이나 환경을 다루면 둘째 자리를 일관되게 쓴다.
`order-management`와 `export-api`처럼 여러 단어가 의미상 한 자리를 이룰 수 있다.

## 분류와 자리

| 첫 자리 | 둘째 자리 | 셋째 자리를 쓰는 경우 | 예 |
| --- | --- | --- | --- |
| `product` | 제품명 | API·웹·작업 처리기·전용 문서를 별도 저장소에서 유지한다. | 전체는 `product-order-management`, API만 따로 운영하면 `product-order-management-api`. |
| `infra` | 기반 자원을 관리하는 실행 환경 | 네트워크·클러스터처럼 독립적으로 관리하는 자원 영역이 있다. | 전체는 `infra-internal`, 별도 네트워크는 `infra-internal-network`. |
| `deploy` | 제품과 실행 환경을 연결하는 배포처 | 한 배포처에서 배포 권한과 복구 책임이 갈린다. | 한 운영 범위는 `deploy-field`, 별도 엣지 범위는 `deploy-field-edge`. |
| `shared` | 사용자가 지원 안내에 따라 실제로 도입하는 형태 | 개별 리소스명을 항상 쓴다. | `shared-plugin-repo-governance`. |
| `docs` | 독자가 공통 자료를 찾는 주제 | 같은 주제 안의 문서 묶음을 독립적으로 유지한다. | 전체는 `docs-engineering`, 별도 온보딩 자료는 `docs-engineering-onboarding`. |

관리 책임이 하나라면 `product`·`infra`·`deploy`·`docs`의 셋째 자리를 생략한다.
버전과 진행 단계는 하위 관리 범위를 나타내는 이름으로 쓰지 않는다.
기업명·고객사명·구현 기술명은 실제 업무나 관리 대상을 식별하는 근거가 있을 때만 쓴다.
배포처는 배포 책임을 식별하는 `deploy`의 둘째 자리에 쓴다.

제품과 함께 변경하는 배포 워크플로는 제품 저장소에 둘 수 있다.
기반 자원의 수명 주기와 공통 플레이북을 관리하는 저장소는 `infra`를 쓴다.
공통 플레이북을 가져와 배포할 버전·인벤토리·롤백을 관리하는 저장소는 `deploy`를 쓴다.
Flux 예제의 `apps/`, `infrastructure/`, `clusters/` 구분은 각 책임을 찾는 근거다. [Flux 저장소 구성](https://github.com/fluxcd/flux2-kustomize-helm-example#repository-structure)

### `shared`의 형태

| 둘째 자리 | 실제로 도입하는 방식 |
| --- | --- |
| `plugin` | 호스트에 플러그인을 등록하거나 설치한다. 같은 단위에 스킬·훅·보조 검사기가 들어갈 수 있다. |
| `skill` | 스킬 자체를 가져다 쓴다. 함께 쓰는 스크립트와 참고 파일을 포함할 수 있다. |
| `bundle` | 하나의 배포물에서 두 개 이상의 단위를 각각 도입해 지원되는 작업을 수행한다. |
| `lib` | 의존성으로 연결하고 공개 인터페이스를 호출한다. |
| `cli` | 사용자나 자동화가 명령줄 진입점을 직접 호출한다. |
| `template` | 제공된 틀을 복제하거나 생성 출발점으로 쓴다. |

지원 안내가 가리키는 기본 도입 경로를 실제 배포물과 대조한다.
같은 기능의 호스트별 설치 경로와 부속 진단 명령은 같은 단위로 센다.
경로가 동등해 대표 형태를 확인하지 못하면 근거를 보완하기 전 최종 이름 적용을 보류한다.
이 프로젝트는 스킬과 훅을 함께 설치하는 경로를 공식으로 제공하므로 `shared-plugin-repo-governance`가 새 이름 후보에 해당한다. [플러그인 설치](../README.md)

## 제안과 적용

README뿐 아니라 실행 진입점·배포 구성·유지 책임과 같은 범주의 기존 이름을 확인한다.
이름을 실제 적용할 때 대상 계정 또는 조직에서 동명 저장소를 확인한다.
형식은 영문 소문자와 숫자로 이은 케밥 케이스다.
이름 검사기는 두 단어 이상인지와 첫 단어가 다섯 분류에 속하는지를 확인한다.
에이전트는 각 자리의 의미를 판단하므로 `shared-plugin`처럼 개별 리소스명이 없는 후보의 적용을 멈춘다.

플랫폼이 이름을 정확히 지정하면 실제 원문과 대상 범위를 확인하고 제품 입력에 허용된 예외를 적용한다.
새 저장소를 분리하는 결정이나 기존 저장소의 이름 변경은 사용자 요청에 따라 별도로 다룬다.
이름을 검토만 요청받았으면 후보와 근거를 제시한다. [예외 기준](../SPEC.md#66-프로필예외와-충돌-처리)

## 수용 사례

| ID | 상황 | 기대 결과 |
| --- | --- | --- |
| N1 | 재고 제품에서 별도로 관리하는 업무 API에 `product-inventory-api`를 제안한다. | 적합.<br>`inventory`는 제품명이고 `api`는 그 제품에서 분리된 구성요소다. |
| N2 | 같은 재고 제품의 API를 사용하는 별도 웹 화면 저장소에 `product-inventory-web`을 제안한다. | 적합.<br>같은 제품은 두 번째 자리 `inventory`를 공유한다. |
| N3 | 품질 제품에서 현장 센서의 수집·전달을 별도로 관리하며 `product-quality-collector`를 제안한다.<br>부수적인 상태 확인 API가 있다. | 적합.<br>실제 분리된 수집 책임을 세 번째 자리에 쓴다. |
| N4 | 주문 관리의 화면과 API를 한 저장소에서 제품 전체로 제공하며 `product-order-management`를 제안한다. | 적합.<br>이 경우 세 번째 자리를 생략한다.<br>폴더만 확인해 제품 범위를 알 수 없는 경우에는 보류한다. |
| N5 | 한 현장 운영 범위에서 주문 관리와 재고 관리의 버전을 함께 관리하면서 `deploy-field-order-management`를 제안한다. | 운영 범위와 이름이 달라 위반.<br>`deploy-field`가 적합하고 제품별 버전은 배포 구성에서 구분한다. |
| N6 | `product-acme-api`의 `acme`가 제품의 업무 영역 대신 실제 고객사를 가리킨다. | 위반.<br>같은 단어가 업무나 제품의 의미를 가진 경우에는 그 의미를 근거로 확인한다. |
| N7 | 문서는 현장 기반 자원을 관리한다고 설명하지만 배포 구성은 기존 환경에 제품 버전을 적용한다.<br>주된 관리 책임을 확인할 수 없다. | `infra`와 `deploy`의 분류를 보류한다.<br>실제로 누가 무엇을 관리하고 복구하는지 확인한다. |
| N8 | 여러 제품이 의존성으로 사용하는 가격 계산 코드를 `shared-lib-price-calculation`으로 부르려 한다. | 적합.<br>호스트 플러그인으로 설치하지 않는다는 근거가 확인된 경우 `shared-plugin-price-calculation`은 위반이다. |
| N9 | 주문 관리 제품에서 별도로 관리하는 내보내기 API 저장소에 `product-order-management-export-api`를 제안한다. | 적합.<br>`order-management`와 `export-api`가 각각 한 자리에 해당한다.<br>이 판정은 별도 저장소를 만드는 결정과 구분한다. |
| N10 | 명명에 적합하지만 사용자는 이름 제안만 요청했다. | 후보와 근거를 제시하는 데서 작업을 끝낸다. |
| N11 | PR 리뷰의 공식 사용 경로는 호스트 플러그인 설치이며, 그 플러그인 내부에 스킬이 있다. | `shared-plugin-pr-review`가 적합하다.<br>스킬 파일만 보고 `shared-skill-pr-review` 또는 `shared-bundle-pr-review`를 선택하면 위반이다. |
| N12 | `inventory_api`, `product_inventory_api`, `product--inventory`, `api-inventory`를 입력한다. | 모두 기계 위반.<br>마지막 후보는 첫 분류를 어기고 나머지는 표기를 어긴다.<br>여러 단어를 포함한 `product-order-management-export-api`는 표기와 첫 분류를 충족한다. |
| N13 | 같은 조직의 다른 저장소가 최종 후보 이름을 사용 중임을 확인한다. | 이름 충돌로 위반.<br>대상 자신의 현재 이름은 충돌에서 제외한다.<br>조회 범위가 부족하면 보류한다. |
| N14 | 참고 문서와 보조 스크립트를 포함한 PR 요약 스킬을 스킬 단위로 직접 가져다 쓴다.<br>같은 리소스를 플러그인으로도 공식 제공하는 경우를 대조한다. | 단독 스킬만 제공하거나 단독 사용이 공식 기본이면 `shared-skill-pr-summary`가 적합하다.<br>플러그인 설치가 공식 기본이면 `shared-plugin-pr-summary`가 적합하다.<br>두 경로가 동등하면 형태 확정을 보류한다.<br>설치 경로나 부속 파일의 개수만으로 `shared-bundle-pr-summary`를 붙이면 위반이다. |
| N15 | 3차원 검사 제품의 실제 제품명이 `3d-inspection`이고 API를 별도로 관리한다. | `product-3d-inspection-api`가 적합하다.<br>`3d-inspection`은 숫자로 시작하는 여러 단어의 제품명이다. |
| N16 | `product-inventory-api`의 표기와 첫 분류는 맞지만 실제 제품명과 구성요소를 확인할 자료가 없다. | 적용 보류.<br>형식 통과나 호출자의 `approved: true`를 의미 확인으로 쓰면 위반이다. |
| N17 | 대분류와 각 자리의 근거는 확인했지만 충돌 조회가 권한 오류로 실패한다. | 적용 보류.<br>충돌을 확인하지 못한 조건부 후보를 제시할 수 있다. |
| N18 | 두 배포물의 플러그인 매니페스트·스킬·검사 스크립트는 같다.<br>A의 공식 도입 단위는 플러그인이고 검사 명령은 설치 확인에 쓴다.<br>B에는 PR 리뷰 플러그인과 커밋 규약 CI 검사를 각각 도입하는 절차가 있고, 각 절차로 자기 작업을 실제 수행할 수 있다. | A는 `shared-plugin-release-review`가 적합하다.<br>B는 `shared-bundle-release-review`가 적합하다.<br>설치 안내의 순서만 바꾸면 같은 판정이다.<br>도입 방식과 독립 실행 여부가 불명확하면 보류한다. |
| N19 | 두 번째나 세 번째 자리를 실제 제품·관리 범위 대신 버전 또는 진행 단계로 채운다.<br>예를 들어 분리된 구성요소가 없는 주문 관리 제품에 `product-order-management-v2`를 붙인다. | 위반.<br>변경된 버전은 제품의 이름이나 독립 관리 범위를 대신할 수 없다. |
| N20 | 후보를 검사한 뒤 실제 도구에 전달할 저장소 또는 이름이 바뀌었다. | 바뀐 대상과 최종 후보를 다시 확인할 때까지 적용을 보류한다. |
| N21 | 실제 적용할 규약 또는 선언한 플랫폼 예외의 원문을 읽지 못했다. | 확인한 근거로 조건부 후보를 제시할 수 있다.<br>읽지 못한 규약이나 예외가 필요한 실제 적용은 확인 후 진행한다. |
| N22 | 플러그인 저장소의 개별 리소스명을 생략한 `shared-plugin`을 사용하려 한다. | 의미 위반.<br>담당자가 동의했거나 기계 표기가 맞아도 세 번째 자리는 필수다. |
