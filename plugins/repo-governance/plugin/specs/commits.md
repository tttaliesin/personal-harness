# K4 커밋 메시지

이력에서 바뀐 행동을 찾을 수 있도록 실제 diff를 보고 `type[(scope)][!]: 한국어 변경 요약`을 쓴다.
여러 커밋에 나눌지 판단할 때 변경 목적을 먼저 확인한다.
한 기능을 고친 코드와 회귀 테스트는 같은 커밋으로 기록할 수 있다.

## 변경 유형

| type | 실제 변경 | 예 |
| --- | --- | --- |
| `feat` | 새 기능이나 동작을 제공한다. | `feat(auth): 토큰 갱신 기능을 추가한다` |
| `fix` | 잘못된 동작을 바로잡는다. | `fix: 만료된 토큰의 재사용을 차단한다` |
| `docs` | 실행 동작을 유지하며 문서·설명·주석을 바꾼다. | `docs: 로컬 실행 절차를 정리한다` |
| `refactor` | 동작을 유지하며 코드 구조를 바꾼다. | `refactor: 토큰 검증 로직을 분리한다` |
| `perf` | 성능 문제를 개선할 목적으로 동작 방식을 바꾼다. | `perf: 중복 파싱을 제거한다` |
| `test` | 테스트만 추가하거나 수정한다. | `test: 만료 토큰 거절 사례를 추가한다` |
| `style` | 실행 의미를 유지하며 코드 포맷만 고친다. | `style: 인증 모듈의 들여쓰기를 맞춘다` |
| `build` | 빌드·패키징·의존성을 바꾼다. | `build: 런타임 의존성 버전을 갱신한다` |
| `ci` | 지속적 통합 실행 절차나 구성을 바꾼다. | `ci: 테스트 결과 업로드를 추가한다` |
| `chore` | 다른 유형에 해당하지 않는 저장소 관리 작업을 한다. | `chore: 사용하지 않는 개발 도구 설정을 정리한다` |
| `revert` | 이전 변경을 되돌린다. | `revert: 토큰 검증 변경을 되돌린다` |

문서 확장자를 가진 스킬이나 실행 규칙도 실제 동작을 바꾸면 그 효과에 따라 유형을 선택한다.
버그 수정과 구조 변경이 함께 있으면 실제 수정 목적에 맞춰 `fix`를 쓴다.
측정값을 적을 때는 실제 비교 조건과 결과를 바탕으로 설명한다.
형식의 근거는 Conventional Commits의 변경 분류이며, 위 유형 목록은 이 플러그인의 공통 기준이다. [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)

## 요약과 본문

한국어 요약에는 무엇이 어떻게 바뀌는지 적는다.
명령·코드 식별자·고유명은 기존 표기를 쓴다.
`scope`는 영역을 찾아보기 쉬워질 때 실제로 쓰는 이름을 영문 소문자 케밥 케이스로 붙인다.

본문이 있으면 제목 다음에 빈 줄을 넣는다.
무슨 선택을 했는지 제목만으로 알기 어렵거나 이행이 필요하면 변경 이유와 영향을 본문에 적는다.
호환성을 깨는 변경에는 제목에 `!`를 붙이고 본문에 영향과 이행 방법을 쓴다.
`revert`에는 되돌린 대상과 이유를 본문에 남긴다.
`BREAKING CHANGE:`로 영향을 표시하면 제목에도 `!`를 쓴다.
안내 문서와 배너의 변경은 `docs:`로 기록할 수 있다.
설치 원본 위치가 바뀌면 사용자가 해야 할 일을 본문에 적는다.

관련 이슈를 남길 때는 실제 관계를 확인한 뒤 `Refs: #123` 같은 참조를 적는다.
이 커밋이 닫을 작업 전체를 해결하는 경우에만 `Closes: #123`를 쓴다.
본문 설명과 관련 작업 표기 사이에 빈 줄을 넣는다.
검증 결과를 적으면 실제 확인한 대상과 결과를 기록한다.

## 적용 범위

새로 작성하는 최종 메시지에 적용한다.
기존 이력을 고치려면 사용자가 해당 작업을 요청해야 한다.
자동 생성 메시지에도 최종 반영 기준을 적용한다.
`fixup!`·`squash!`·`amend!`는 대상과 정리 방법이 확인된 임시 작업에 사용할 수 있다.
최종 통합에서는 정리한 메시지를 적용한다.
외부 기여의 확인된 `area: summary` 관례는 유효한 제품 입력의 정확한 영역과 실제 외부 원문을 대조한 뒤 적용한다. [공통 예외 기준](../SPEC.md#66-프로필예외와-충돌-처리)

지원 훅은 실제 사용할 메시지의 제목 형식, 유형, 빈 줄, 자리표시자와 관련 작업 표기를 검사한다.
에이전트는 최종 메시지를 현재 편입 후보와 맞추고 관련 사실이 바뀌면 확인한다.
호스트에서 편입 범위를 미리 확정할 수 없는 작업에는 대상을 먼저 stage하는 방식을 사용한다.
문구만 요청받았으면 확인한 변경을 바탕으로 후보를 제공한다.

## 수용 사례

표의 `M`은 후보 메시지, `T`는 실제 편입 후보를 가리킨다.

| ID | 상황 | 기대 결과 |
| --- | --- | --- |
| CMT1 | 만료 토큰을 허용하던 코드를 거절하도록 고쳤다.<br>`M`은 `fix: 만료된 토큰의 재사용을 차단한다`다. | 적합.<br>실제 버그 수정과 한국어 요약이 일치한다. |
| CMT2 | 실행 절차 문서만 바꿨다.<br>`M`은 `docs: 로컬 실행 절차를 정리한다`다. | 적합.<br>본문 없이 목적을 식별할 수 있다. |
| CMT3 | 새 토큰 갱신 기능을 추가했다.<br>현재 영역 문서에 `auth`가 유효하며 `M`은 `feat(auth): 토큰 갱신 기능을 추가한다`다. | 적합.<br>선택 scope의 의미와 현재 용례를 확인했다. |
| CMT4 | 실제 실패 시 갱신 코드를 고쳤다.<br>`M`은 `fix(auth): 로그인 실패 시 refreshToken을 갱신하지 않는다`이며 `auth` 용례가 확인됐다. | 적합.<br>기술 식별자는 한국어 설명 안에서 유지할 수 있다. |
| CMT5 | CMT1의 변경에 `만료된 토큰의 재사용을 차단한다`만 쓴다. | 위반.<br>필수 type과 구분자가 없다. |
| CMT6 | CMT1의 변경에 `fix: Prevent expired token reuse`를 쓴다. | 위반.<br>사람이 읽는 설명이 영문이다. |
| CMT7 | 실제 후보는 실행 절차 문서뿐인데 `fix: 토큰 검증 오류를 수정한다`를 쓴다. | 위반.<br>type과 설명이 실제 변경과 다르다. |
| CMT8 | 설정 관리 파일을 정리하며 `update: 설정을 정리한다`를 쓴다. | 위반.<br>허용 집합 밖의 type이다. |
| CMT9 | CMT1의 변경에 `fix: 수정`을 쓴다. | 위반.<br>문법은 맞아도 실제 변경을 식별할 수 없다. |
| CMT10 | 후보 tree의 내용을 읽지 못해 type과 요약을 대조할 수 없다. | 보류.<br>메시지를 추측해 커밋하지 않는다. |
| CMT11 | API의 `token` 필드를 삭제해 호출자 수정이 필요한데 `feat(api): 인증 응답의 토큰 필드를 변경한다`만 쓴다. | 위반.<br>`!`와 영향·이행 본문이 빠졌다. |
| CMT12 | CMT1의 변경에 실행 기록 없이 `테스트 통과`를 적었으며 작성자도 미실행이라고 밝혔다. | 위반.<br>알고 있는 실행 사실과 검증 주장이 충돌한다. |
| CMT13 | CMT1의 변경에 `fix: Prevent expired token reuse 수정`을 쓴다. | 위반.<br>한국어 단어 추가가 한국어 설명을 대신하지 못한다. |
| CMT14 | 유효한 영역 문서와 관련 이력이 인증 영역을 `auth`로 정했다.<br>같은 영역의 `M`에 `authentication`을 쓴다. | 위반.<br>확인된 같은 영역의 용례를 나눈다. |
| CMT15 | 유효 문서가 `auth`를 토큰 인증, `login`을 로그인 화면으로 구분한다.<br>로그인 화면만 고치고 `fix(login): 로그인 오류 안내를 바로잡는다`를 쓴다. | 적합.<br>서로 다른 scope의 의미를 확인했다. |
| CMT16 | 실제 관련 이슈 `#123`의 일부를 수정했다.<br>`M`에 `Refs: #123`을 적고 완료 주장은 없다. | 적합.<br>관련 작업의 참조와 종료를 구분한다. |
| CMT17 | CMT16의 부분 수정에 `Closes: #123`을 쓴다. | 위반.<br>확인된 해결 범위가 전체 완료를 충족하지 않는다. |
| CMT18 | 요청이 `#123` 연결을 요구했지만 이슈의 존재나 종료 조건을 조회할 수 없다. | 보류.<br>필요한 참조를 확인 없이 적용하지 않는다. |
| CMT19 | 봇이 CMT1의 변경에 `fix: Prevent expired token reuse`를 생성했다. | 위반.<br>일반 봇 메시지의 한국어 기준은 같다. |
| CMT20 | 작업 브랜치에 임시 `fixup! fix(auth): 만료된 토큰의 재사용을 차단한다`를 만들려 한다.<br>대상 커밋과 최종 반영 전 정리 방법을 확인했다. | 임시 단계에 적합.<br>최종 반영에는 정리한 메시지를 적용한다. |
| CMT21 | `fixup!`·`squash!`·`amend!` 중 하나를 임시 작업에서 쓴 뒤 최종 대상 브랜치의 메시지로 남기려 한다. | 최종 반영 전에 해당 메시지를 정리한다.<br>임시 작업에서 허용한 효과를 최종 이력에 그대로 적용하지 않는다. |
| CMT22 | 임시 메시지를 요구하지만 대상 커밋 관계나 정리 방법을 확인하지 못했다. | 보류.<br>예외 성립의 필수 근거가 없다. |
| CMT23 | `M`의 형식 검사만 통과했고 `T`의 diff는 읽지 못했다. | 전체 판정은 보류.<br>형식 통과가 내용 적합을 증명하지 않는다. |
| CMT24 | 실제 메시지 파일이나 편입 후보를 읽지 못했거나 호출한 검사가 오류로 끝났다. | 해당 변경의 자료를 확보하거나 실행 오류를 해결한다.<br>실제로 실행한 훅은 오류를 성공으로 처리하지 않는다. |
| CMT25 | 검토 뒤 훅이나 작업 과정에서 실제 메시지 또는 편입 후보가 바뀐 사실을 확인했다. | 바뀐 메시지와 후보를 현재 diff와 다시 대조한다. |
| CMT26 | 형식에 맞는 메시지와 `approved: true`만 있고 실제 diff를 확인하지 않았다. | 현재 편입할 diff에서 요약과 실제 변경이 일치하는지 확인한다. |
| CMT27 | 실제 호출되는 `.md` 검토 리소스를 고쳐 개인 기록을 제품 원본으로 허용하던 판정을 바로잡았다.<br>현재 동작 변경과 버그 근거를 확인했고 `fix: 개인 기록의 제품 편입을 차단한다`를 쓴다. | 적합.<br>확장자가 문서여도 실행 판단을 바꾼 수정이므로 효과에 맞는 type을 쓴다.<br>같은 변경을 설명만 고친 `docs`라고 쓰는 대조 후보는 위반이다. |
| CMT28 | 실행 경로가 읽지 않는 검토 제안 명세에 파일 포함 판정 예시만 보완했다.<br>`M`은 `docs: 파일 포함 기준의 판정 사례를 보완한다`다. | 적합.<br>제안 명세 작성을 실제 실행 동작 구현으로 표현하지 않는다. |
