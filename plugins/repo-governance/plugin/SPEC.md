# governance-tool 명세

일곱 저장소 규약을 에이전트가 작성과 판단에 사용할 공통 리소스로 제공한다.
작업 에이전트는 실제 저장소 자료로 작성안을 만들고, 채택한 저장소의 하네스 훅은 지원하는 변경에서 확정할 수 있는 조건을 확인한다.

## 1. 목적

이름·설명·README·커밋·브랜치·PR·파일 위치가 실제 업무와 사용 방법을 설명해야 한다.
팀원은 자신이 쓰는 하네스에서 같은 기준과 사례를 참조할 수 있어야 한다.
검사는 지원되는 변경 입구에서 실제로 반영될 후보에 맞춰 실행한다.

## 2. 사용자 요구와 제약

- 관련 규약과 현재 자료를 바탕으로 권고안을 작성한다.
- 비교할 기존 관례가 있으면 현재 저장소와 업무에 유효한지 대조한다.
- 작업 내용의 실제 의미와 검증 주장은 작업 에이전트가 확인한다.
- 실제 후보의 기계 검사는 지원 하네스 연결이 수행한다.
- 수동 검사는 명시적으로 요청받았을 때 사용할 수 있다.

Codex Desktop·Claude Code·pi의 공통 스킬과 연결을 유지한다.
각 하네스에서 자동으로 검사하는 도구와 지원 상태는 관측된 근거로 밝힌다.
GitHub Free에서도 로컬과 지원되는 에이전트 연결로 사용할 수 있다.

| --- | --- | --- |

| [K7 파일](specs/file-inclusion.md) | 실제 소비 경로와 유지 책임을 보고 저장 위치를 정한다. | 명시한 출력 경계의 충돌·제외와 편입 후보에 들어간 선언 출력물을 검사한다. |

## 4. 책임과 산출물

공통 스킬과 상세안은 권고 기준과 선택 이유를 제공한다.
템플릿은 작성할 때 참고할 수 있는 기본안이다.
공통 검사기는 명시한 자료를 읽고 확인한 기계 조건을 반환한다.
하네스 연결은 지원하는 실제 요청을 판별하고 검사의 실패를 호스트 응답에 반영한다.
로컬 도입·진단·배포 안내와 선택형 CI는 사용자와 유지보수자가 필요한 진입점을 제공한다.

### 4.1 범위에 포함하지 않는 일

저장소의 생성·분리·가시성·종료와 조직의 담당 배정·권한 설정은 운영자가 결정한다.
예를 들어 이름 후보 결정은 저장소 신설이나 이름 변경 권한과 별개다.
에이전트는 실제 저장소 작업과 사용자 권한을 기존 Git·GitHub 및 하네스 도구에 맡긴다.
팀에서 요구하는 코드 리뷰, 테스트와 배포는 각 프로젝트의 절차를 따른다.

## 5. 규약별 상세 명세 요건

### 5.1 설명과 메시지의 언어 방향

설명과 README의 안내, 커밋 요약, PR 본문의 일반 설명은 한국어로 작성한다.
제품명·기술 식별자·실제 명령·원문 오류는 필요에 따라 그대로 쓴다.
브랜치와 저장소 이름은 각 명명 규약의 표기를 따른다.
PR 제목은 변경을 식별하기 좋은 표현을 선택한다.

### 5.2 파일 포함·제외 규칙

제품이 현재 버전에서 빌드·사용·재현하는 데 쓰는 원본, 명세, 테스트 소스와 fixture는 해당 저장소에서 유지한다.
공통 실행 원본은 공통 저장소에서 유지하고 제품별로 필요한 연결과 입력을 둔다.
개인 작업 자료와 실행 결과는 확인된 로컬 제외 경로나 제품 밖에 둔다.
혼합 파일은 공유 원본과 개인 결과물을 나누는 방법을 제안한다.
쓰임을 확인하지 못한 경우 임시로 로컬에 두고 편입할 근거를 확인한다.
도구 이름이나 파일 확장자가 바뀌어도 실제 용도와 소비 경로를 본다. [K7 상세안](specs/file-inclusion.md)

#### 5.2.1 보관 위치와 포함 기준

플러그인 실행 파일은 `plugin/`에 둔다.
개발 테스트와 회귀 fixture는 실제로 소비할 개발 영역에 둔다.
실행별 증거와 원시 로그는 책임자가 정한 공유 작업 공간이나 로컬에 둔다.
배포 내용이 바뀌면 실제 설치본의 파일 목록과 읽는 경로를 대조한다. [설치·배포 범위](specs/file-inclusion.md#설치배포-범위와-파일-배치)

#### 5.2.4 생성·수정 전

작업 에이전트는 출력 목적과 실제 위치를 파악해 권하는 위치를 제안한다.
일반 미추적·ignored 파일을 파일 상태만으로 거절하지 않는다.
제품이 명시한 로컬 전용 출력 경계가 있으면 지원 파일 쓰기 도구에서 경로·추적 원본 충돌·실제 Git 제외를 검사한다.
기존 파일을 덮어쓸 위험이 확인되면 안전한 대상 위치를 확보한다.

#### 5.2.5 commit 직전

커밋의 실제 후보에서 선언한 로컬 전용 출력이 편입되면 지원 훅이 거절한다.
에이전트는 혼합 파일이나 쓰임을 확인하지 못한 파일의 편입을 보류하고 필요한 부분만 확인한다.
실제 Git 후보를 확정할 수 없는 경우 편입할 파일을 먼저 stage하는 방식을 안내한다.

### 5.3 저장소 이름(K1)

첫 분류는 `product`, `infra`, `deploy`, `shared`, `docs`다.
같은 관리 대상을 찾을 때는 분류와 둘째 자리를 공유한다.
독립된 책임을 표시할 때 셋째 자리를 쓰고, `shared`는 개별 리소스명을 셋째 자리에 항상 쓴다.
`shared`의 형태는 공식 도입 경로와 실제 배포 단위의 쓰임으로 결정한다.
기계 검사에서 표기와 첫 분류가 맞아도 에이전트는 자리의 의미와 이름 충돌을 확인한다. [K1 상세안](specs/naming.md)

## 6. 적용 절차와 판정

### 6.1 작업 효과

| 작업 | 작업 에이전트 | 지원 훅 |
| --- | --- | --- |
| 조회와 초안 | 필요한 근거로 후보와 판단 이유를 제시한다. | 실제 변경이 없는 작업을 계속한다. |
| 저장소 이름·설명 변경 | 실제 대상·이름의 의미와 충돌·설명의 현재 사실을 확인한다. | 해당 후보의 K1·K2 기계 조건을 검사한다. |
| 로컬 파일 생성·편집 | 실제 대상에 맞게 작성하고 출력 위치를 고른다. | 지원 파일 쓰기의 명시한 출력 경계를 검사한다. README 초안 구조는 검사하지 않는다. |
| 커밋 | 실제 diff와 편입 파일을 읽고 메시지를 작성한다. | 한 훅 호출에서 메시지·Git 후보·편입할 README를 검사한다. |
| 지원 원격 파일 변경 | 실제 대상 README 내용과 경로를 확인한다. | 변경할 README의 후보를 검사한다. |
| 브랜치 생성·이름 변경 | 목적·기준 ref·동명 브랜치의 기존 쓰임을 확인한다. | 새 이름과 실제로 확인할 수 있는 기준·동명 여부를 검사한다. |
| PR 등록·수정·머지 점검 | 실제 변경과 검증을 설명하고 요청한 단계에 필요한 조건을 확인한다. | 지원하는 등록·수정과 명시적 squash 요청의 실제 자료에서 해당 규약을 검사한다. |

지원 연결은 도구의 호출 인자를 읽는다.
인용·도움말·조회에 포함된 명령어와 실제로 변경할 요청을 구분한다.
복합 도구에서 지원 범위를 확인하지 못한 경우 검사된 부분과 미확인 부분을 남긴다.
적용 규약이 있는 것으로 식별했지만 필요한 후보를 확정할 수 없는 경우 확인 가능한 형태로 대상과 입력을 정한다.

### 6.2 공통 규칙 버전과 제품별 입력

하네스에 플러그인을 설치한 뒤 규약을 사용할 로컬 clone에 한 번 도입한다.
같은 Git 공용 디렉터리를 사용하는 연결된 worktree는 clone 도입 기록을 공유한다.
개별 제품 설정이 필요한 경우 기준 ref·출력 경계·외부 계약 등을 제공한다.
기존 worktree별 도입 기록과 제품 입력은 그 worktree에서 우선 적용한다.
외부에 있는 명시적 제품 입력도 기존 명령을 통해 사용할 수 있다.
[설치와 도입](README.md)에서 현재 사용하는 도입 명령을 확인한다.

| 실제 대상 | 연결 동작 |
| --- | --- |
| 도입 기록과 기존 제품 입력이 없음 | 자동 규약 검사를 미적용하고 작업을 계속한다. |
| clone 도입 기록만 있음 | 같은 clone의 연결된 worktree에서 공통 기준을 적용한다. 제품 설정은 선택이다. |
| 유효한 기존 worktree별 도입 또는 제품 입력 | 해당 worktree의 기존 입력으로 같은 변경을 검사한다. |
| 기존 worktree별 도입 기록이 가리키는 제품 입력이 없음 | 누락된 입력을 보고하고 해당 검사를 보류한다. |
| 선택된 설정이 손상됐거나 구형 계약을 해석할 수 없음 | 그 원인을 표시하고 해당 검사를 보류한다. |

공통 리소스의 일치와 무결성은 배포 manifest로 확인한다.
설정 스키마와 계약이 호환되는 설치 갱신은 기존 채택과 설정을 계속 사용한다.
기존 스키마의 `bundle.version`과 `bundle.sha256` 필드는 호환 읽기를 위해 허용한다.
호환 갱신에는 해당 필드의 해시를 새로 만들거나 도입을 다시 기록할 필요가 없다.
기존 설정을 해석할 수 없는 변경이 생기면 달라진 기준과 이행 방법을 제공한다.
하네스가 요구하는 신뢰 절차는 실제 변경에 맞춰 진행한다.
[제품 입력](skills/repo-governance/references/repository-policy.md)에서 현재 입력 형식을 확인한다.

### 6.3 검사 대상과 실제 작업의 연결

검사는 실제 도구 인자, 선택된 worktree·경로, 확인할 수 있는 Git index·OID 또는 원격 조회 자료를 읽는다.
README를 커밋할 때는 문서 내용과 상대 링크의 대상을 같은 편입 후보에서 확인한다.
직접 원격에 반영할 파일은 지원되는 요청에서 저장소와 ref, 전체 파일 후보를 대조한다.
실제 대상·내용·기준이 달라진 사실을 확인하면 바뀐 부분을 현재 자료로 다시 대조한다.
읽은 식별값의 효력은 확인 당시 대상에 한정된다.
실제 변경과 호스트의 최신 조건 적용은 기존 실행 도구가 담당한다.

### 6.4 실행 입구와 연결부의 준비 확인

Codex Desktop 훅·Claude Code 훅·pi 확장이 같은 공통 기준과 검사기를 사용한다.
직접 CLI와 선택형 CI는 전달받은 자료에 읽기 전용 검사를 수행한다.
설치 확인과 실제 세션에서 도구 호출·차단을 관측하는 시험은 각각 근거를 남긴다.
훅의 누락·비활성화·신뢰·timeout 때문에 실제 호출을 확인하지 못하면 그 상태를 보고한다.

### 6.5 실패 시 복구

응답이 알려준 대상·설정·연결 문제만 확인한다.
예를 들어 제품 경로가 다르면 현재 worktree의 설정을 먼저 확인한다.
설치 자료의 불일치면 확인된 배포물로 복구하고 호스트가 요구한 신뢰 절차를 따른다.
실패를 성공으로 기록하지 않으며 수행하지 않은 차단을 보고하지 않는다.
파일·원격의 쓰기 없이 확인한 내용과 이번 요청에서 수행 가능한 다음 동작을 알린다.

### 6.6 프로필·예외와 충돌 처리

README의 배치·본문 절·시각 자산은 독자와 현재 프로젝트에 맞춰 고른다.
기존 `readmeProfile`과 각 제품의 디자인 문서는 근거가 있는 배치 선호에 쓸 수 있다.
`governance-tool`의 소스 디자인은 저장소의 `docs/DESIGN.md`에서 정한다.

플랫폼의 정확한 이름 요구, 실제 외부 기여의 영역·언어 관례, 호스트나 자동화가 부여한 브랜치 접두어는 원문을 확인한다.
유효한 설정의 대상·범위·기간을 실제 계약과 대조한다.
`approved: true` 같은 표시는 예외의 근거로 사용하지 않는다.
실제 예외의 확인에 필요한 자료가 없으면 일반 권고안이나 확인할 항목을 제시한다.

## 7. 에이전트별 공통 적용

[공통 스킬](skills/repo-governance/SKILL.md)은 현재 작업의 규칙과 근거를 찾는 입구다.
추가 검토 모델, 수집 서버, 별도 쓰기·머지 엔진 없이 작업 에이전트와 기존 하네스가 적용한다.
하네스마다 동작하는 도구 이름이 달라지면 실제 입구와 지원하지 않는 형태를 유지보수 문서에 기록한다.

## 9. 상세안과 남은 결정

### 9.1 일곱 규약의 기준 원본

3절의 각 상세안에서 정상·위반·보류 사례와 선택 근거를 확인한다.
[README](templates/README.md)와 [PR](templates/PULL_REQUEST.md) 템플릿은 독자와 변경에 맞춰 적용한다.

### 9.2 채택과 제품별 입력

제품의 기존 버전·설치 위치·사용자 승인 범위를 도입 문서에서 확인한다.
설치 안내는 기본 도입 경로를 먼저 제공한다.
제품별 입력의 작성이나 갱신은 실제로 프로젝트 고유 조건이 필요한 경우에 적용한다.

### 9.3 구현과 남은 검증

동일한 업무 요청으로 개편 전후의 권고안이 실제 독자와 근거를 반영하는지 비교한다.
Codex Desktop의 실제 세션에서 정상 통과, 커밋 전 파일·README 위반 거절, 호환 갱신 뒤 재도입 없이 동작하는지를 확인한다.
Claude Code·pi의 실제 모델 세션 검증은 보류 상태로 유지한다.
검증 방법과 증거 저장은 [검증 방법과 증거](skills/repo-governance/references/verification.md)를 따른다.

## 10. 개발 순서

1. 일곱 권고안과 공통 스킬이 실제 사례를 안내하도록 작성한다.

## 11. 구성과 검사기 계약

### 11.1 공통 구성

`plugin/`은 사용자가 설치하는 실행 배포 트리다.
manifest는 공통 규약·템플릿·스킬·검사기·연결·도입 자료의 실제 파일을 식별한다.
테스트와 fixture, 검증 증거, 이 저장소의 README 디자인은 소스 체크아웃의 유지 영역에 둔다.
패키지에 들어간 파일 경로와 내용이 배포 의도와 일치하는지 확인한다.

163개 상세 사례와 57개 공통 사례의 ID·조건·기대 결과는 일곱 상세안과 이 문서의 T/A/FI/E 표에서 읽는다.
기계 fixture는 참조할 사례 ID와 실행 입력을 유지한다.
체크아웃의 사례 목록, 기계 fixture 실행, 실제 세션에서 보인 동작은 각각의 근거를 사용한다.

### 11.2 읽기 전용 검사 계약

직접 CLI는 JSON 한 건을 stdin으로 받고 JSON 한 줄을 stdout으로 반환한다.
요청은 `{schemaVersion:3,operation:"check",check:string,sources:Source[],context:Context}`다.
Context는 `{repository?:string,bundlePath:string,productPath?:string,baseRef?:string}`다.
지원하는 검사 종류와 사용 가능한 자료는 다음과 같다.

| 종류 | Source |
| --- | --- |
| `name`, `description`, `branch` | `{kind:"text",text:string}` 한 개 |
| `readme`, `commit-message` | text 또는 `{kind:"file",path:string}` 한 개 |
| `file-scope` | `{kind:"index"}` 또는 `{kind:"revision",revision:string}` 한 개, 또는 file 목록 |
| `pull-request` | `pr` 또는 `pr-create` 한 개 |

`pr`은 `{kind:"pr",number:integer,headOid:string,baseOid:string,title:string,body:string}`이다.
`pr-create`는 `{kind:"pr-create",repository:string,headRef:string,baseRef:string,headOid:string,baseOid:string,title:string,body:string,draft:boolean}`이다.
원격 대상은 지원하는 하네스 연결이 실제 조회 자료로 확인한다.
직접 검사의 PR 자료는 호출자가 제공한다.
README text는 제품 루트 기준 상대 `path`를 사용할 수 있다.
경로가 없으면 제품 루트의 `README.md`를 기준으로 링크를 확인한다.
커밋 입구는 index 내용을 읽어 문서와 링크를 검사한다.
일반 CLI의 README text/file 입력 계약은 유지한다.
확인 가능한 원격 직접 반영은 요청의 대상·ref·변경 파일을 기준으로 관련 확인을 수행한다.

결과의 `scope`는 `mechanical`이다.
`decision`은 `pass`, `violation`, `needs-context`, `error` 중 하나다.
종료 코드는 각각 0, 2, 3, 1이다.
`findings`는 확인한 문제, `observed`는 읽은 대상과 식별값, `semanticChecks`는 작업 에이전트가 근거를 확인할 질문이다.
이 출력으로 별도 승인이나 변경 권한을 부여하지 않는다.
기존 CLI 사례와 옵션은 [읽기 전용 검사기](skills/repo-governance/references/checker.md)에서 확인한다.

### 11.3 작업 에이전트의 절차

1. 요청에 해당하는 규약과 실제 자료를 읽는다.
2. 근거에 맞는 문안과 실행 계획을 작성한다.
3. 실제 변경이 요청됐으면 기존 도구에서 진행한다.
4. 사용자가 별도로 검사를 요청하면 대상과 범위를 정해 읽기 전용 검사기를 사용한다.

### 11.4 연결 수용 사례

| ID | 시험 | 기대 결과 |
| --- | --- | --- |
| E1 | 세 하네스가 현재 배포물의 스킬과 연결을 사용한다. | 같은 규칙을 찾아 해당 작업을 지원한다. |
| E2 | 정상 이름·커밋·README와 각 기계 위반을 비교한다. | 정상 작업은 이어진다.<br>README의 지원 커밋·원격 직접 반영에서 실제 후보 위반을 거절한다. |
| E3 | 표기와 첫 분류는 맞지만 실제 하위묶음이나 셋째 자리의 근거가 없다. | 기계 조건 통과와 에이전트의 이름 적용 보류를 확인한다. |
| E4 | 선언 출력이 실제 index에 들어 있다. | 해당 편입을 거절한다. |
| E5 | 지원 일반 커밋·명시적 amend와 `-a`·경로 지정 호출을 비교한다. | 실제 검사한 Git 후보와 지원하지 않는 방식을 확인한다. |
| E6 | 입력 오류·리소스 실패·결과 nonzero를 보낸다. | 확인된 호출에서 실패를 반환한다. |
| E7 | 훅 누락·비활성화·신뢰 미확인·timeout을 비교한다. | 실제 호스트 동작을 관측하고 연결 상태를 기록한다. |
| E8 | 관측한 내용·worktree·head/base가 바뀐다. | 현재 후보로 관련 내용을 다시 확인한다. |
| E9 | 지원 입력과 미해석 복합 입력·인용문을 비교한다. | 실제 검사한 작업과 범위를 구분한다. |
| E10 | 선택형 CI에 실제 revision·PR 자료를 준다. | 읽은 후보와 기계 결과를 확인한다. |
| E11 | 이름이 같은 개인 색인·제품 fixture·혼합 자료의 위치를 결정한다. | 실제 소비 경로로 위치를 판단한다. |
| E12 | 새 환경에서 설치·도입하고 호환 갱신을 거친다. | 기존 설정을 유지한 채 정상 변경과 위반을 재현한다. |
