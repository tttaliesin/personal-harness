# K6 풀 리퀘스트

검토자가 왜 이 변경이 필요하고 무엇이 바뀌었는지 읽을 수 있게 쓴다.
제목은 변경을 식별할 수 있는 표현을 선택한다.
본문의 일반 설명은 한국어로 쓰고 명령·식별자·실제 오류 메시지는 원문을 사용할 수 있다.

## 변경과 확인을 쓰는 방법

작은 변경은 이유·변경·확인 결과를 문장 몇 개로 적어도 충분하다.
운영·호환성·자료에 영향이 있으면 누가 무엇을 해야 하는지 덧붙인다.
독립적인 비교나 확인이 여러 개라면 소제목이나 목록을 추가한다.
[PR 템플릿](../templates/PULL_REQUEST.md)의 섹션 이름과 배치는 필요에 따라 바꾼다.
Ollama의 API 문서 PR은 문서와 스키마 변경을 요약하고 확인할 명령을 따로 적었다. [Ollama PR #16877](https://github.com/ollama/ollama/pull/16877)

실제로 바뀐 내용은 현재 head와 base의 비교 범위에서 읽는다.
검증 결과에는 실제 확인한 대상·방법·결과를 적는다.
실행하지 못했거나 실패한 확인이 있으면 실제 상태와 남은 항목을 적는다.
이미 있는 결과를 인용하면 현재 후보에 유효한지 확인한다.
문서 오탈자처럼 실행 영향이 없는 작업에는 문장과 링크의 대조 결과를 쓸 수 있다.
관련 작업을 인용하면 실제 연결과 변경 범위를 확인한다.

## 등록·수정·머지

등록과 수정에는 실제 저장소, 대상 PR 또는 생성할 head·base를 확인한다.
연동 시험이 남아도 그 이유를 정확히 적은 검토 초안을 만들거나 요청된 PR을 등록할 수 있다.
사용자가 검토만 요청했으면 현재 변경과 확인 결과를 설명한다.
대상 브랜치를 변경하면 새 기준에서 비교 범위와 검증 결과가 유효한지 확인한다.

지원 훅은 실제 변경의 빈 제목, 알려진 자리표시자, 닫히지 않은 코드 블록, 확인 가능한 대상 불일치를 검사한다.
고정 섹션 이름은 요구하지 않는다.
검증 내용의 사실성과 영향 설명은 에이전트가 실제 결과와 대조한다.

머지가 요청되면 현재 head·base, 필요한 제품 검증과 호스트 조건을 확인한다.
squash로 남길 메시지에는 K4를 적용하고 실제 편입 후보에는 K7을 적용한다.
PR 제목과 최종 커밋 메시지는 각 용도에 맞게 작성할 수 있다.
실제 반영은 기존 GitHub 도구의 지원 범위에서 수행한다. [연결과 역할](../SPEC.md#6-적용-절차와-판정)
