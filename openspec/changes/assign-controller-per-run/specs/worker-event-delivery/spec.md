# 워커 이벤트 전달 변경

## MODIFIED Requirements

### Requirement: Enable event delivery only within an authorized project and run

CLI는 확인한 프로젝트와 호스트의 현재 실행에 대해 그 실행의 컨트롤러가 사용자에게 푸시를 위임받은 경우에만 푸시 경로를 제공해야 한다(MUST).

#### Scenario: 프로젝트별 푸시 위임 확인

- **WHEN** 실행을 배정하는 채팅의 위임에 `scope: "project"`와 `pushEvents: true`가 있다.
- **THEN** CLI는 프로젝트와 호스트가 일치하는 해당 채팅의 워커 실행에 푸시 정보를 제공할 수 있다.
- **AND** 다른 채팅의 푸시 위임은 이 실행에 적용하지 않는다.
- **AND** 호출자가 푸시 위임을 받지 않았거나 사용자가 위임을 철회했다면 요청에 푸시 값을 추가해도 새 실행에 푸시 권한이 생기지 않는다.
- **AND** 푸시 위임 여부와 관계없이 실행의 컨트롤러는 허용된 수동 관찰 경로를 사용할 수 있다.

### Requirement: Configure only the managed permission hook and retain Desktop trust

`push-config`는 프로젝트가 관리하는 승인 기록 훅만 적용하거나 제거해야 한다(MUST).
다른 훅과 Desktop 신뢰 설정은 보존해야 한다(MUST).

#### Scenario: 적용 전 미리 보기와 기존 훅 보존

- **WHEN** 로컬 프로젝트에 등록된 컨트롤러가 `push-config`를 호출한다.
- **THEN** `apply: true`가 없으면 계획한 설정을 반환한다.
- **AND** 권한을 가진 호출자가 적용을 요청하면 프로젝트 `.codex/hooks.json`의 관리 대상 `PermissionRequest` 그룹만 추가하거나 교체한다.
- **AND** 관리 대상 그룹에는 `journal-approval` 명령만 넣는다.
- **AND** 관리 대상 그룹을 교체할 때 이전 그룹의 고정 수신자 `mcp_tool`을 제거한다.
- **AND** Desktop에서 훅을 실행하도록 허용하는 절차는 사용자의 Hooks UI 확인을 따른다.

#### Scenario: 관리한 훅 제거

- **WHEN** 현재 또는 이전 푸시 위임을 받은 채팅이 관리 훅 제거를 요청하고 다른 채팅에 푸시 위임이 없다.
- **THEN** CLI는 현재 명령 경로나 제공한 이전 명령 경로가 정확히 일치하는 그룹만 제거할 수 있다.

#### Scenario: 다른 채팅이 사용하는 관리 훅을 제거하려는 경우

- **WHEN** 한 채팅이 관리 훅 제거를 요청하고 다른 채팅에 푸시 위임이 남아 있다.
- **THEN** CLI는 훅을 유지하고 제거 요청을 거절한다.

### Requirement: Publish approval metadata and terminal results to a project journal

푸시 발행자는 프로젝트와 워커 실행을 대조할 수 있는 사건을 프로젝트별 저널에 기록해야 한다(MUST).
`push-result`는 등록된 실행에서 수신자를 확인하고, 종료 결과를 저장한 뒤에만 후속 메시지 호출 계획을 반환해야 한다(MUST).

#### Scenario: 승인 요청 기록과 후속 메시지 전송

- **GIVEN** 이전 배포본의 승인 기록 훅과 고정 수신자 `mcp_tool`이 함께 설치돼 있다.
- **WHEN** 워커 채팅에서 Desktop 승인 요청이 발생한다.
- **THEN** 기존 훅은 승인 사건을 저널에 기록하고 고정된 채팅에 후속 메시지를 보낼 수 있다.
- **AND** 실행을 배정한 채팅만 해당 저널 사건을 처리한다.

#### Scenario: 저널 전용 관리 훅으로 승인 요청 기록

- **WHEN** `journal-approval`이 프로젝트 안의 작업 디렉터리, 워커 채팅과 턴 식별자가 담긴 승인 훅 입력을 받는다.
- **THEN** CLI는 대조에 필요한 승인 메타데이터를 프로젝트 루트의 `.local/worker-orchestrator/push/` 아래 프로젝트별 `inbox.sqlite`에 기록한다.
- **AND** 관리 훅은 승인 사건의 후속 메시지를 보내지 않는다.
- **AND** 해당 실행의 컨트롤러는 다음 턴에 `push-inbox`로 승인 사건을 조회한다.
- **AND** 사용자는 해당 워커 채팅의 Desktop 승인 UI에서 승인 원문을 확인하고 응답한다.

#### Scenario: 워커의 종료 결과 기록과 재발행

- **WHEN** 등록된 워커가 현재 `runId`의 유효한 `completed` 또는 `failed` 결과를 `push-result`에 제출한다.
- **THEN** CLI는 프로젝트, 작업과 실행을 대조하고 실제 워커 채팅 ID와 호스트가 등록 정보와 일치하는지 확인한다.
- **AND** CLI는 저장된 `task.controllerRef`에서 수신자를 확인한다. 이전 실행에 해당 참조가 없으면 원래 프로젝트 컨트롤러를 사용한다.
- **AND** CLI는 결과를 저널에 저장한 뒤 배정한 컨트롤러 채팅을 대상으로 `send_message_to_thread` 호출 계획을 반환한다.
- **AND** 워커는 직접 사용자 허가를 확인한 경우에만 그 호출 계획으로 후속 메시지를 보낸다.
- **AND** 워커는 저널에 보낸 것과 같은 결과 JSON으로 턴을 끝낸다.
- **AND** 같은 결과를 재발행하면 같은 사건 ID를 반환한다.
- **AND** 같은 실행에서 결과나 턴이 달라진 재발행은 충돌로 처리한다.

#### Scenario: 배정한 채팅에서 종료 결과 전송을 허가한 경우

- **GIVEN** 워커가 종료 결과를 기록했고 콜백의 수신자가 실행을 배정한 채팅과 일치한다.
- **WHEN** 워커가 직접 사용자 허가를 아직 확인하지 못했다.
- **THEN** 워커는 공식 Desktop 조회로 배정한 채팅의 원본 사용자 메시지를 확인한다.
- **AND** 사용자가 해당 채팅으로 결과를 보내도록 허가한 경우 워커는 Desktop 도구에서 전송을 한 번 시도한다.
- **AND** 직접 사용자 허가가 확인되지 않거나 Desktop이 전송을 거절하면 워커 채팅에 미전송 상태를 알린다.
- **AND** 종료 결과는 저널에서 조회할 수 있다.

#### Scenario: 발행에 사용할 실행이나 수신자가 일치하지 않는 경우

- **WHEN** 다른 워커, 호스트 또는 이전 실행의 요청이거나 요청에 담긴 수신자가 저장된 수신자와 일치하지 않는다.
- **THEN** CLI는 결과 발행 요청을 거절한다.
- **AND** CLI는 대조할 수 없는 실행이나 저장에 실패한 사건에 대해 후속 메시지 호출 계획을 반환하지 않는다.

#### Scenario: 사용자 허가가 실행 한 건의 종료 결과에 한정된 경우

- **GIVEN** 등록된 컨트롤러 채팅에서 사용자가 그 채팅으로 이번 결과를 한 번 보내도록 허가했다.
- **WHEN** 컨트롤러가 허가의 출처를 배정에 포함한다.
- **THEN** CLI는 허가를 그 실행 및 배정 채팅에 묶는다.
- **AND** 등록된 워커는 종료 결과를 발행하고 배정 채팅은 그 실행의 결과를 관찰하고 처리 완료를 기록할 수 있다.
- **AND** 같은 결과를 동시에 발행해도 CLI는 동일한 사건 ID를 반환하고 한 응답에만 전송 계획을 반환한다.
- **AND** 이 허가의 적용 범위는 현재 실행의 종료 결과다.
- **AND** 컨트롤러는 프로젝트 승인 훅을 관리할 때 프로젝트 위임을 사용한다.

#### Scenario: 등록된 실행에서 워커 연결 기록보다 먼저 도착한 종료 결과

- **GIVEN** 현재 실행에 같은 호스트와 Desktop 프로젝트를 대상으로 한 워커 생성 동작이 저장돼 있다.
- **WHEN** 호스트가 워커를 시작했지만 컨트롤러가 아직 생성 응답으로 워커를 연결하지 않았다.
- **THEN** CLI는 해당 실행의 저장된 컨트롤러를 종료 결과의 수신자로 사용한다.
- **AND** 컨트롤러는 실제 생성 응답으로 확인한 워커의 채팅 ID와 호스트를 사건의 출처와 대조한 뒤에만 결과를 처리한다.

### Requirement: Correlate notices with host identity and preserve pending events

`push-inbox`는 호스트가 제공한 출처와 프로젝트 저널을 대조해야 한다(MUST).
CLI는 실제 호출자가 소유한 작업의 현재 실행에 해당하는 사건만 반환해야 한다(MUST).

#### Scenario: Desktop이 전달한 후속 메시지로 사건 확인

- **WHEN** 컨트롤러가 종료 결과의 후속 메시지를 Desktop 콜백으로 받는다.
- **THEN** 컨트롤러는 Desktop이 전달한 `source_thread_id`와 메시지 본문의 워커 채팅 ID를 대조한다.
- **AND** 컨트롤러는 메시지 본문의 프로젝트와 호스트를 등록 정보와 대조한다.
- **AND** CLI는 사건이 현재 실행과 런타임 호출자에게 속하는지를 확인한다.
- **AND** 후속 메시지가 잘못됐거나 늦어도 호출자가 소유한 다른 처리 가능한 사건을 조회할 수 있다.

#### Scenario: 후속 메시지의 전달과 컨트롤러 턴 확인

- **WHEN** 컨트롤러가 후속 메시지의 전달 또는 새 턴 시작 여부를 확인한다.
- **THEN** 컨트롤러는 Desktop이 전달한 메시지의 발신 채팅 ID와 사건 식별자를 대조한다.
- **AND** 턴 ID를 관측할 수 있으면 메시지가 기록된 턴 ID를 전달 전의 컨트롤러 턴 ID와 대조한다.
- **AND** 같은 실행 중 턴에 메시지가 기록되면 기존 턴 반영으로 판정한다.
- **AND** 메시지 전달로 시작한 다른 턴에 메시지가 기록되면 새 턴 시작으로 판정한다.
- **AND** 전송 접수나 저널 기록만 관측했으면 실제 전달과 새 턴 시작은 미확인으로 둔다.

#### Scenario: 등록보다 빨리 도착하거나 새 실행보다 오래된 사건

- **WHEN** 사건이 워커 연결 기록보다 먼저 오거나 현재 `runId`에 해당하지 않는다.
- **THEN** CLI는 그 사건을 현재 실행의 완료 근거로 적용하지 않는다.
- **AND** 워커가 연결된 뒤에는 보류한 사건을 다시 대조할 수 있다.
- **AND** 종료 결과의 후속 메시지가 도착하지 않아도 이후 컨트롤러 턴의 `push-inbox`에서 미처리 사건을 찾을 수 있다.

#### Scenario: 같은 프로젝트의 다른 컨트롤러가 사건을 조회

- **GIVEN** 채팅 A와 B가 각자 푸시 위임을 받았고 A의 실행에 저널 사건이 있다.
- **WHEN** B가 `push-inbox`를 호출하거나 A의 사건 ID와 콜백 본문을 전달한다.
- **THEN** CLI는 A의 사건이나 워커 원문 조회 계획을 B에게 반환하지 않는다.
- **AND** A의 `push-inbox`는 해당 사건을 계속 처리 대상으로 조회할 수 있다.

### Requirement: Verify current worker evidence before applying a push event

`push-observe`는 런타임 호출자가 현재 실행의 컨트롤러인지 확인해야 한다(MUST).
CLI는 사건과 동일한 워커·호스트·현재 실행·턴의 확인된 원문을 사용해야 한다(MUST).

#### Scenario: 종료 결과가 확인된 경우

- **WHEN** 컨트롤러가 등록 워커의 현재 턴 원문을 읽고 유효한 최종 보고가 저널의 결과와 일치함을 확인한다.
- **THEN** CLI는 종료 결과를 관찰에 연결하고 실행의 컨트롤러가 평가할 수 있게 한다.
- **AND** 조회 실패, 턴 불일치, 종료 전 상태 또는 결과 불일치는 보류한다.

#### Scenario: 승인 플래그가 확인된 경우

- **WHEN** 실행의 컨트롤러가 사건에 해당하는 활성 워커 턴에서 실제 승인 대기 플래그를 확인한다.
- **THEN** CLI는 사건 ID로 승인 대기를 기록하며 같은 사건을 다시 관찰해도 대기를 중복 추가하지 않는다.
- **AND** 이미 종료된 턴의 승인 사건은 새 대기를 만들지 않는다.

#### Scenario: 실행을 소유하지 않은 호출

- **WHEN** 실행의 컨트롤러가 아닌 채팅이 그 사건의 원문을 가지고 `push-observe`를 호출한다.
- **THEN** CLI는 해당 실행에 관찰이나 대기를 기록하지 않는다.

### Requirement: Acknowledge only selected handled events in controller workflow

컨트롤러는 처리했거나 이미 정리한 사건의 ID만 `push-ack`에 전달해야 한다(MUST).
`push-ack`는 런타임 호출자가 소유한 작업과 연결되는 호환 사건만 확인 처리해야 한다(MUST).

#### Scenario: 일부 사건만 처리한 경우

- **WHEN** 컨트롤러가 결과 평가 또는 승인 표시를 마친 사건의 ID를 제출한다.
- **THEN** CLI는 요청된 ID 중 해당 컨트롤러에게 속한 호환 사건만 확인 처리한다.
- **AND** 요청에 포함하지 않았거나 다른 컨트롤러 또는 다른 프로젝트에 속한 사건은 그대로 남는다.
- **AND** 같은 확인을 반복해도 처리 상태나 평가를 중복 적용하지 않는다.

#### Scenario: 배정 이후 컨트롤러 턴 종료

- **WHEN** 푸시를 사용하는 컨트롤러가 배정 기록과 현재 처리 가능한 사건을 마친다.
- **THEN** 컨트롤러는 워커 종료를 기다리는 호출을 추가하지 않고 현재 턴을 끝낸다.
- **AND** 종료 결과는 Desktop 콜백을 받은 턴이나 이후 컨트롤러 턴에서 처리한다.
- **AND** 승인 사건은 컨트롤러의 다음 턴에 조회하고 워커 채팅에서 사용자가 응답할 수 있도록 대기 상태를 전달한다.
