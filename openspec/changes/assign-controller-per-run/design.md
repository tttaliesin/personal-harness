# 실행별 컨트롤러 설계

## Context

프로젝트 레코드는 작업 경로와 Desktop 소속을 `projectId`에 연결한다.
실행에는 `taskId`, 현재 `runId`, 연결된 워커와 미확정 Desktop 동작이 있다.
승인 훅의 `mcp_tool`은 설정 파일에 저장한 채팅 ID만 수신자로 사용할 수 있다.

## Goals / Non-Goals

같은 Desktop 프로젝트 안에서 각 채팅이 자신의 위임으로 작업을 배정하고 그 결과를 받는다.
실행 소유권의 범위는 기존 프로젝트의 작업 경로와 Desktop 소속 안으로 한정한다.
개발 소스와 검증용 패키지에 이 설계를 적용한다. 공개 기준선과 배포 파일은 현재 배포의 근거로 보존한다.

## Decisions

### 실제 현재 채팅을 확인하고 등록한다

CLI는 런타임의 현재 채팅 ID와 호스트를 사용한다.
호스트는 런타임 값을 사용하거나 공식 Desktop 응답에서 현재 채팅으로 확인한 호스트를 사용한다.
공식 프로젝트 목록과 첫 페이지부터 현재 채팅을 포함한 페이지까지의 이력으로 작업 경로와 Desktop 소속을 대조한다.
현재 채팅을 확인하면 다음 페이지를 조회할 필요가 없다.

CLI는 프로젝트 조회와 새 채팅 등록을 상태 저장소의 한 트랜잭션에서 처리한다.
최초 호출은 프로젝트 정체성을 함께 생성한다.
다른 채팅이 먼저 프로젝트를 만들었으면 같은 정체성에 현재 채팅을 등록한다.
기존 `claim` 입력을 받는 호출 경로에서도 등록 판단은 같은 근거를 사용한다.

### 프로젝트 정체성과 실행 소유권을 따로 저장한다

프로젝트에는 작업 범위와 Desktop 소속을 저장한다.
채팅별 등록에는 확인한 `hostId`와 `threadId`, 위임의 출처와 동작별 권한을 저장한다.
처음 등록한 채팅에 부여하는 기본 권한은 모두 `false`다.
기존 프로젝트 위임은 원래 등록된 채팅에서만 읽는다.

`dispatch`는 실행 예약과 같은 트랜잭션에서 요청을 보낸 채팅의 참조를 `task.controllerRef`에 저장한다.
작업을 이어서 실행할 때 같은 소유자를 사용하므로 이전 요청이나 회신이 다른 채팅으로 이동하지 않는다.
이전 실행을 읽을 때 참조가 비어 있으면 원래 `project.controllerRef`를 사용한다.
공유 상태 저장소를 유지하면 기존 작업·워커·동작 기록을 그대로 대조할 수 있다.

CLI는 소유자를 판정하는 공통 경로를 작업 조회, 실행 명령, 저널 조회와 확인에 사용한다.
목록 조회는 현재 실행의 소유자로 필터링한다.
개별 작업 명령은 반환이나 변경 전에 런타임 호출자와 소유자를 대조한다.
현재 `runId`를 확인하는 기존 규칙은 늦게 도착한 사건이 다음 실행에 적용되는 일을 막는다.

### 종료 결과의 수신자를 등록된 실행에서 읽는다

`push-result`는 실제 워커 채팅과 호스트를 등록된 프로젝트, 작업, 현재 실행에 대조한다.
CLI는 실행의 소유자 참조로 기존 `send_message_to_thread` 호출 계획을 만든다.
컨트롤러 참조를 입력으로 받은 경우에는 저장한 값과 일치하는지 확인한다.
CLI는 사건을 저널에 저장한 뒤 호출 계획을 워커에 반환한다.
워커는 배정한 채팅의 원본 사용자 메시지에서 결과 전송 허가를 확인할 수 있다.
Desktop은 실제 전송을 승인하거나 거절한다.
배정에 일회성 결과 허가가 들어오면 실행이 그 출처를 저장한다.
저널에 같은 실행 결과를 동시에 발행해도 최초 저장 응답만 후속 메시지 계획을 받는다.
이후 배정과 재시도는 각각의 실행에 해당하는 허가를 사용한다.
워커 연결 기록보다 먼저 종료 결과가 도착하면 소유자는 실행 기록으로 확인하고, 결과 처리는 실제 워커 연결을 확인할 때까지 보류한다.

### 결과를 채택한 뒤 워커를 보관한다

컨트롤러는 합의한 후속 배정이나 유지 요청이 있으면 `keepWorker: true`를 전달한다.
그 밖에는 CLI가 결과를 채택할 때 현재 실행의 보관 허가 또는 프로젝트 단위 보관 위임을 확인한다.
배정 시 기록한 일회성 보관 허가는 해당 실행에서만 사용한다.
채택과 보관 성공은 각각 기록한다.
워커의 보관 상태는 실제 Desktop 응답으로 확정한다.

### 승인 훅은 저널에 기록한다

승인 훅의 별도 `mcp_tool`은 기록 명령이 확인한 실행 소유자를 인수로 받을 수 없다.
관리하는 `PermissionRequest` 그룹에는 `journal-approval` 명령만 둔다.
이 명령은 사용자 결정 없이 승인 메타데이터를 기록한다.
실행의 컨트롤러는 다음 턴에 저널 사건과 해당 워커 턴의 실제 승인 대기를 대조한다.
사용자는 워커 채팅의 Desktop 승인 UI에서 승인 요청을 처리한다.

## Risks / Trade-offs

- 같은 프로젝트에 컨트롤러가 여러 명이면 프로젝트 ID만으로 사건을 분류할 수 없다. 저널 조회와 확인 모두 현재 호출자의 작업 소유권을 확인한다.
- 종료 결과의 전송 호출이 접수돼도 Desktop 전달은 지연될 수 있다. 저장한 사건은 해당 컨트롤러가 이후 턴에서 다시 조회할 수 있다.
- 승인 요청은 컨트롤러의 새 턴을 시작시키지 않는다. 승인 UI는 워커 채팅에 바로 표시하고 컨트롤러는 다음 턴에 기록을 확인한다.

## Migration Plan

1. 기존 프로젝트의 컨트롤러 참조와 사용자 위임을 읽을 수 있도록 개발 소스를 갱신한다. 이전 실행에서 원래 소유자가 조회되는지 확인한다.
2. 이전 관리 훅을 교체하는 경로에서 고정 수신자 `mcp_tool`을 제거한다. 적용 미리 보기와 결과에서 관리 그룹과 사용자 훅을 확인한다.
3. 개발 소스로 만든 검증용 패키지와 격리 상태 디렉터리에서 동작을 확인한다. 검증 전후 공개 배포본의 파일이 같은지 확인한다.
