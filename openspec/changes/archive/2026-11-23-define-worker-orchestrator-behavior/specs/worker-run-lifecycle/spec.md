# Spec Delta

## Purpose

컨트롤러가 같은 프로젝트에서 작업을 배정하고, 실제 Desktop 응답을 근거로 실행 상태를 이어받는다.
중복 생성, 미확정 응답, 승인 대기와 보관을 각 실행의 식별자에 연결해 관리한다.

## ADDED Requirements

### Requirement: Plan delegated work for an authorized project worker

컨트롤러와 CLI는 현재 프로젝트의 권한, 연결된 워커와 실행 상태로 `dispatch`가 요청할 호스트 동작을 정해야 한다(MUST).

#### Scenario: 독립 작업의 범위를 배정

- **WHEN** 컨트롤러가 운영을 맡은 프로젝트에서 서로 독립적인 작업을 워커에 배정한다.
- **THEN** 각 작업에 서로 다른 `taskId`를 부여하고 파일 소유 범위가 겹치지 않게 정한다.
- **AND** 각 실행은 배정 계획, Desktop 호출, 실제 응답 기록의 순서를 유지한다.

#### Scenario: 새 워커와 기존 워커 선택

- **WHEN** 새 실행을 시작할 수 있고 해당 작업에 워커가 연결돼 있지 않다.
- **THEN** CLI는 생성 권한을 확인한 뒤 현재 Desktop 프로젝트의 워커 생성 계획을 반환한다.
- **AND** `reuseOnly: true`인 경우에는 연결된 워커가 있어야 한다.
- **AND** 연결된 워커가 있으면 동일한 대화의 후속 전달을 계획한다. 그 대화가 보관돼 있으면 복원 권한과 후속 전달 권한을 확인해 복원을 먼저 계획한다.

#### Scenario: 관련 실행이 진행 중이거나 소속이 달라진 경우

- **WHEN** 같은 작업에 활성 실행, 대기, 미확정 호스트 동작 또는 평가하지 않은 구조화 작업이 남아 있다.
- **THEN** 기존 실행을 유지하고 상태와 남은 조건을 확인한다.
- **AND** `dispatch`는 호출 시점의 권한과 워커 상태를 다시 확인한다. 이전 상태 조회만으로 새 실행이 허용되지 않는다.
- **AND** 워커의 Desktop 프로젝트 연결이 달라지면 이전 워커에 새 요청을 전달하지 않는다.

### Requirement: Reuse a request identity without overlapping runs

각 작업의 `requestId`는 요청 본문, 실행 프로필, 작업 명세와 연결하며, 한 작업의 활성 실행이 겹치지 않게 해야 한다(MUST).

#### Scenario: 같은 배정 요청의 재전송

- **WHEN** 같은 프로젝트·작업의 `requestId`와 동일한 요청을 다시 받는다.
- **THEN** CLI는 기존 실행에 연결된 상태와 실행 가능한 동작을 반환한다.
- **AND** 새 `runId`와 워커 생성 동작을 추가하지 않는다.
- **AND** 같은 요청 ID로 본문, 프로필 또는 작업 명세를 바꾸면 `REQUEST_REPLAY_MISMATCH`를 반환한다.
- **AND** 같은 요청 ID가 이전 실행에 속하면 현재 작업의 상태를 조회하되 그 이전 요청을 새로 실행하는 동작은 반환하지 않는다.

#### Scenario: 서로 다른 요청이 같은 작업에 동시에 도착

- **WHEN** 같은 작업을 대상으로 별개 요청이 동시에 실행을 예약하려 한다.
- **THEN** 시작 조건을 충족한 한 실행만 활성화된다.
- **AND** 다른 요청은 실행이나 미확정 동작이 남아 있는 동안 진행할 수 없다.

### Requirement: Record the actual host receipt for the current action

호스트 동작의 상태는 계획된 `action.id`에 대응하는 실제 응답으로만 확정해야 한다(MUST).

#### Scenario: 생성 응답을 현재 실행에 연결

- **WHEN** 컨트롤러가 생성 계획을 확인하고 Desktop에서 실제 호출을 수행한다.
- **THEN** `record`에 계획한 동작 ID와 실제 응답 또는 계약에 맞는 증빙을 남긴다.
- **AND** 생성 응답은 예정한 호스트와 일치해야 한다. 동일한 워커 대화는 둘 이상의 작업에 연결할 수 없다.

#### Scenario: 후속 전달 및 보관·복원 응답 연결

- **WHEN** 컨트롤러가 후속 전달, 보관 또는 복원의 실제 응답을 기록한다.
- **THEN** CLI는 현재 동작과 같은 워커인지 확인한다.
- **AND** 보관과 복원은 각각 일치하는 `archived: true` 또는 `archived: false` 응답을 요구한다.

#### Scenario: 응답 기록의 재전송

- **WHEN** 이미 확정한 동작의 같은 응답을 다시 제출한다.
- **THEN** CLI는 확정 상태를 유지한다.
- **AND** 실행이나 동작 식별자가 오래됐거나 확정한 응답과 다르면 현재 상태를 덮어쓰지 않는다.

### Requirement: Reconcile an uncertain host action before retrying creation

실제 생성 여부를 확인할 수 없는 호스트 응답은 조정이 필요한 상태로 기록하고, 확인 전 새 생성 동작을 보류해야 한다(MUST).

#### Scenario: 생성 응답 유실 또는 해석 불가

- **WHEN** 생성 도구의 응답이 유실되거나 워커 식별자를 검증할 수 없다.
- **THEN** CLI는 호스트 동작을 미확정 상태로 유지한다.
- **AND** 다른 CLI 프로세스에서 다시 요청해도 같은 호스트 동작을 조정할 때까지 추가 생성을 계획하지 않는다.

#### Scenario: 호스트가 생성 대기만 확인한 경우

- **WHEN** 호스트가 구체적인 대화 ID 없이 `clientThreadId`로 생성 대기만 반환한다.
- **THEN** CLI는 응답을 받아들이고 동작 결과를 `unknown`으로 기록한다.
- **AND** 현재 대화를 확보한 것으로 확정하기 전까지 생성 동작을 다시 발행하지 않는다.

#### Scenario: 생성 시작 전의 확정 거절

- **WHEN** 컨트롤러가 실제 생성이 시작되기 전에 거절됐음을 확인해 기존 동작에 `rejected`와 근거를 기록한다.
- **THEN** CLI는 그 동작을 거절로 확정한다.
- **AND** 기존 워커가 없는 해당 작업에서 권한과 요청 조건이 충족되면 새 `requestId`로 생성 계획을 요청할 수 있다.

### Requirement: Track and resolve each pending request within its run

CLI는 승인 또는 입력 대기를 실행의 `waitId`로 구분하고, 실제 해소 근거가 확인된 항목만 해소해야 한다(MUST).

#### Scenario: 승인과 입력 대기가 함께 있는 실행

- **WHEN** 같은 실행에 승인 요청과 사용자 입력 요청이 함께 들어온다.
- **THEN** 관찰 결과는 각 요청의 종류와 식별자를 보존한다.
- **AND** `resolve`로 한 요청의 해소 근거를 기록해도 나머지 요청은 대기 상태를 유지한다.
- **AND** 같은 실행에서 이미 해소한 요청의 기록을 반복하면 상태를 중복 변경하지 않는다.

#### Scenario: 식별자가 없는 승인이 다시 발생한 경우

- **WHEN** 식별자 없는 승인 신호를 해결한 뒤 같은 턴이 다시 실행 중이라는 관찰을 거쳐 새 승인 신호가 나타난다.
- **THEN** CLI는 해결한 승인과 구분되는 새 대기 ID를 사용한다.

### Requirement: Preserve the worker and reset verification on a followup

같은 작업의 후속 실행은 기존 워커 대화에 새 `runId`를 연결하고 현재 실행의 검증 상태를 새로 시작해야 한다(MUST).

#### Scenario: 보관한 워커로 이어서 진행

- **WHEN** 후속 전달과 복원 권한이 있는 컨트롤러가 보관된 워커를 재사용한다.
- **THEN** CLI는 복원 계획을 반환하고 실제 복원 응답을 기록한다.
- **AND** 워커 연결과 후속 전달 권한이 여전히 유효하면 같은 대화의 전달 계획을 반환한다.
- **AND** 복원 뒤 전달 권한이 회수되면 복원 상태는 보존한다. 권한을 다시 확인한 뒤 같은 요청을 이어서 처리할 수 있다.
- **AND** 새 실행은 이전 실행의 결과 검증을 승계하지 않는다.

### Requirement: Archive only a reviewed and accepted worker result

보관 계획은 현재 실행의 성공, 근거가 있는 검증 통과, 결과 채택, 대기와 미확정 동작 해소 및 보관 권한을 모두 확인한 뒤에만 제공해야 한다(MUST).

#### Scenario: 후속 작업이 없는 성공 결과

- **WHEN** 프로젝트 범위의 상시 보관 위임이 있고 컨트롤러가 현재 결과를 채택하면서 `keepWorker: false`를 지정한다.
- **THEN** CLI는 그 워커의 보관 계획을 반환할 수 있다.
- **AND** 컨트롤러는 실제 보관 응답을 동일한 `action.id`로 기록한다.
- **AND** 보관 동작이 이미 대기 중이면 같은 계획을 재사용한다.

#### Scenario: 채택한 실행의 보관을 명시적으로 요청

- **WHEN** 보관 권한이 있는 컨트롤러가 검증하고 채택한 현재 실행에 `archive`를 요청한다.
- **THEN** CLI는 현재 워커의 보관 계획을 반환하거나 이미 보관된 상태를 반환한다.
- **AND** 완료 결과의 채택 조건을 충족하기 전에 요청하면 보관 계획을 반환하지 않는다.

#### Scenario: 보관 조건이 충족되지 않거나 워커 유지 요청

- **WHEN** 실행 실패, 검증 근거 누락, 미해소 승인·입력 대기 또는 미확정 호스트 동작이 남아 있다.
- **THEN** CLI는 워커를 보관할 수 있는 상태로 확정하지 않는다.

#### Scenario: 채택한 실행의 워커 유지

- **WHEN** 결과는 채택할 수 있고, 자동 보관 위임과 `keepWorker: false`가 함께 성립하지 않는다.
- **THEN** 컨트롤러는 기존 대화를 후속 작업에 사용할 수 있다.
