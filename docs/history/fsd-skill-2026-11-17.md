# 공식 FSD Skill 검토와 두 PC 적용

2026년 11월 17일 사용자 요청으로 공식 FSD Skill을 두 PC에 추가했다.
적용 전에 공식성·내용·검증 한계를 검토했다.
자동 선택 범위는 이미 FSD를 채택한 저장소의 구조 작업으로 제한했다.
Steiger와 ArchUnitNET은 저장소별 도입 원칙만 반영했다.

## 공식성과 검토 범위

[FSD 공식 Docs for LLMs](https://fsd.how/docs/llms/)는 이 스킬을 공식 커뮤니티 스킬로 명시한다.
같은 문서가 `feature-sliced/skills`를 설치 원본으로 직접 안내한다.
따라서 저장소의 이름이나 자체 홍보 문구만으로 공식성을 판단하지 않았다.

공식 스킬은 FSD v2.1 문서를 기반으로 하지만 문서 원문을 그대로 복사한 것은 아니다.
문서 간 규칙 충돌에 대한 선택과 프레임워크 통합 보충이 있으며 원본에서 이를 설명한다.
pages-first·필요한 레이어만 추가·공개 API·의존성 방향은 현재 공식 문서와 비교했다.
기존 widgets 레이어를 무효로 보거나 스킬만으로 제거하는 지침은 추가하지 않았다.

원본은 [평가 설명](https://github.com/feature-sliced/skills/blob/5e95aaebb84541742686e56352b7569acf4306f1/feature-sliced-design/evals/README.md)에서 의미적 답변 정확도를 CI가 평가하지 않는다고 명시한다.
형식·참조 무결성 검사와 실제 모델의 올바른 설계 판단은 구분한다.
공식 배포 여부를 정확도·개발 속도 향상이나 품질 인증의 근거로 삼지 않는다.

## 원본과 등록 방식

| 항목 | 확인 값 |
|---|---|
| 원본 저장소 | `https://github.com/feature-sliced/skills` |
| 원본 경로 | `feature-sliced-design` |
| 고정 commit | `5e95aaebb84541742686e56352b7569acf4306f1` |
| commit 날짜 | `2026-10-11T14:11:32Z` |
| 방법론 버전 | FSD v2.1 — 패키지 릴리스 번호와 구분 |
| 파일 수 | 12개: SKILL.md, 참조 9개, 평가 자료 2개 |
| 전체 콘텐츠 SHA256 | `e4b8d804195f7c7799cf7f96ae4f92ec3da612a35f2888c8fb31a94f4f24a589` |
| upstream 라이선스 선언 | README의 MIT 선언을 원본 그대로 보관 |

기본 `skill-installer`의 GitHub 설치 도우미로 정확한 commit의 디렉터리 전체를 가져왔다.
모든 파일의 Git blob SHA1을 해당 commit의 tree와 비교해 원본 일치를 확인했다.
파일별 SHA256과 출처는 [출처 기록](../../dependencies/feature-sliced-skill.json)에 남겼다.
원본 본문·참조·평가 자료는 수정하지 않았다.
스킬 디렉터리에는 실행 스크립트·hook·상주 프로세스가 없다.
본문에 포함된 Steiger 설치·실행 예제는 실행하지 않았다.

배포 소스 스킬 목록인 `scripts/harness.py`의 `SKILLS`와 `REPOSITORY_SKILLS`에 등록했다.
배포 대상은 두 PC의 `~/.agents/skills/feature-sliced-design`이다.
실제 plugin manifest가 없는 스킬을 Git 플러그인·MCP registry 항목으로 위장하지 않았다.
기존 `registry.toml`과 의존성 lock은 그대로 유지했다.

두 PC의 적용된 사용자 지침 SHA256은 `ff4083420b5bf8018c931b855cb19813c5c4fe7b7e3ebe4edd5193622ccbd5da`다.
설치 직후에는 기존 hook·신뢰·앱 런타임 설정을 포함한 config.toml 전체를 바이트 단위로 비교했다.
FSD 블록을 제외한 기존 사용자 지침도 동일함을 확인했다.
repo-governance 개발 소스에는 쓰기 작업을 수행하지 않았다.

## 선택 범위와 검사 도구

저장소 지침·설계 문서·설정으로 FSD 채택이 확인됐을 때 관련 구조 작업에 자율적으로 선택한다.
명시적인 스킬 호출은 필요하지 않다.
React나 폴더 이름만으로 채택을 추정하지 않는다.
비채택·불확실한 저장소는 기존 구조를 유지한다.
기존 버전·예외·프레임워크·라우팅·SSR·API·배포 경로와 개발 규칙을 우선한다.

Steiger와 ArchUnitNET의 버전·규칙·실행 명령은 각 저장소에서 정한다.
이번에는 두 도구를 설치하거나 프로젝트 설정·hook·필수 검사 단계를 추가하지 않았다.

## 저장소 검증

`task test`는 286개 테스트를 실행했고 284개 통과·환경 조건에 따른 2개 생략·실패 0개로 끝났다.
새 원본 무결성 검사는 모든 파일과 upstream README의 SHA256을 출처 기록과 비교한다.
기존 영속 상태 테스트에 FSD 원본·중첩 참조·평가 파일을 포함했다.
원격 설치 payload와 실제 npm 패키지에 모든 FSD 파일이 포함되는지도 검사했다.

Homelab의 새 CLI 세션에서 동일한 파일 배치 질문을 임시 FSD 채택·비채택 저장소에 각각 보냈다.
질문에는 스킬 이름이나 스킬을 읽으라는 지시를 넣지 않았다.
채택 여부는 임시 저장소의 AGENTS.md와 README에 명시했다.
두 PC 모두 FSD 저장소에서만 공식 SKILL.md 읽기를 선택했고 비채택 저장소에서는 선택하지 않았다.
그러나 실제 읽기 명령은 Homelab의 설치된 앱 실행 경로 오류와 Roylabs의 runner pipe 연결 시간 초과로 실패했다.
따라서 자동 선택 시도는 관찰했지만 스킬 본문을 읽고 적용하는 전체 경로의 성공은 확인하지 못했다.
두 사례는 읽기 전용·일회성 `codex exec --ephemeral` 세션으로 실행했다.
이는 단일 사례의 관찰이며 일반적인 선택률이나 구조 준수의 결정적 보증은 아니다.

Roylabs에서는 첫 CLI 검증이 입출력 초기화 오류로 시작 전에 종료됐다.
입력을 닫고 순차 실행한 재시도는 두 답변을 완료했으나 위의 읽기 실패는 남았다.
사용자 설정·hook 신뢰·원본 스킬을 변경해 이 검증을 우회하지 않았다.
두 PC의 실제 스킬 설치·전체 파일 해시 검증과 이 CLI 한계는 별개로 보고한다.

CLI 검증 뒤 Roylabs에서 repo-governance 파일 추가·수정과 hook 신뢰 해시 변화가 관찰됐다.
설치 직후의 83개 파일 동일 검사 이후 발생한 변화이며 이번 작업은 해당 경로에 쓰지 않았다.
이 변화의 원인을 단정하지 않고 현재 파일과 신뢰 상태를 복원하거나 수정하지 않았다.

최종 Roylabs task check는 잔여 변경·누락 0개였고 FSD 원본 12개 파일도 일치했다.
작업용 임시 소스·CLI 로그·테스트 저장소는 두 PC에서 정리했다.
원래 적용 백업과 공개되지 않는 요약 검증 기록은 보관한다.
